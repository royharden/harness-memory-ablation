# Future Linux controller boundary

Source construction only. No backend, task input, process, model, permit, signature,
isolation or billing behavior has been executed or proved. P0/K/L, independent
appointments, runtime activation, keys and spending remain unavailable. This source
does not enforce or prove container isolation by itself and creates no container,
image, CI or deployment configuration.

`workspace.TaskDelivery` binds admitted execution-item ID/hash separately from exact
visible UTF8 stdin payload/hash (bounded1MiB). `RuntimePermit` binds attempt/launch,
policy, task delivery, capability record, isolation context, expiry, actual M9 run,
and admission/activation/capability/isolation/finite-liability/begin/task-delivery
receipt hashes. These objects and hashes are untrusted artifacts, not execution
authority. No public wire fields are added to harnessrun/1.

`RuntimeVerifier` is a future operator-owned integration. It must authenticate
signatures, revocation, current source access/admission, exact pinned capabilities,
task-input interpretation, actual M9 begin and finite liability, and *the executing
Linux namespace/mount/home/config/network/image/binary context*. The only provided
implementation, `UnavailableRuntimeVerifier`, refuses. A returned typed attestation
must bind the exact permit/context, be fresh and within expiry. No CLI flag loads
a verifier or grants execution. Declaration consistency and typed attestations do
not replace genuine external verification.

Native adapters still refuse by default. Future `PreparationAuthorization` requires
all four capability classes verified with exact version/image/binary/provider/
settings pins, permit capability digest and trusted verification before prepare
returns data. Task bytes go to stdin, never argv. Candidate Claude text mode and
Codex `-` syntax are hypotheses until exact-version verification; a caller cannot
invent that receipt to enable the default verifier.

`ProcessController` owns the sole future subprocess creation/termination source.
Its default verifier and durable journal are unavailable; typed execute arguments
alone do not enable it. A future `DurableLaunchJournal` must atomically persist
single use of both attempt and launch IDs across workers/crashes, bind actual M9
begin and immutable hashes, persist spawn intent before the OS call and started/
cleanup/final states. Unknown begin/claim/spawn/journal effects stay consumed and
retain liability. There is no memory-cache replay fallback or monetary settlement.

After trusted permission and durable claim, Linux source launches only the exact
absolute executable, `shell=False`, a new session/process group, admitted cwd and
explicit exact environment names/values, with no host environment inheritance.
Fresh HOME must match policy. Nonblocking stdin/output handling bounds combined
stdout/stderr bytes and wall time by attempt timeout, launch deadline and permit
expiry; cancellation and partial input become explicit outcomes. Raw output is a
private capture requiring later redaction/access controls, not a public event or
report field. Source never discovers environment secrets or reads credential files.

Cleanup records pending first, then uses bounded TERM/KILL against only owned
groups, including after leader exit. `group_state` requires a trusted live exclusive
PID-namespace/ownership lease through each signal, prevention of PGID reuse/escape,
and proof that *all* descendants are gone. A PID probe, process-group disappearance
or leader wait cannot prove that. If ownership/namespace integration, reaping or
durable cleanup confirmation is uncertain, the result remains cleanup_pending.
Every outcome retains monetary liability; separate future M9 reconciliation owns
any settlement. No current journal or namespace verifier can satisfy these duties.

Remaining integrations are precise: authenticated RuntimeVerifier; durable DL3/M9
launch journal and recovery mapping; isolation namespace/descendant ownership and
cleanup evidence; exact CLI input/capability proof; capture redaction/storage;
operator/P0/resource activation. All process-group, stdin/backpressure, cancellation,
deadline/output overflow and crash/recovery checks remain deferred. Source review
is neither a runtime demonstration nor instrument/product acceptance.
